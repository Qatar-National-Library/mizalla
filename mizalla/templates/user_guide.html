01

Sign-in and access

Sign in with an account created by an administrator on the Members screen. The first administrator is created with flask --app mizalla create-admin, which prompts interactively for name, email, and a password of at least 12 characters.

Roles are per project. They describe a person's relationship to one project, not to you, so the same person can run one project as Project Manager, build another as a team member, and observe a third as a vendor. A member can also hold several roles on the same project.

Project visibility comes only from holding any role on that project. Task ownership, meeting attendance, and administrator status alone do not grant visibility. A project outside your scope returns 404 rather than revealing its existence.

The six roles

RoleWhat it grants
Delegated PMActs for the Project Manager on this project. Same access as a PM, including assigning roles.
Project teamBuilds the project: adds and edits tasks, steps, meetings, and documents. Adding the "Project Manager" team role makes this member a PM of the project.
Delegated BackupA stand-in for a Delegated PM. Same access as a Developer, but cannot assign roles.
ClientRead-only: sees the project and downloads its documents.
StakeholderRead-only.
VendorRead-only.

Who can manage a project

A member manages a project by holding the Delegated PM role on it, or by being a Project Team member who also holds the Project Manager team role. Administrators can always manage any project. Only those managers — and admins — can assign or remove roles on a project, over both the web form and the REST API. A PM of one project cannot staff another.

The Project Manager flag on the Members screen is a separate, directory-level marker: it lets that member open the New project form and makes them the Project Manager of anything they create. It does not grant authority over projects they did not create. Existing setups are converted on first start, so anyone who relied on the old behaviour keeps it where they were already a team member.

Edit boundaries — Project Team members, Delegated PMs, and Delegated Backups can create and edit project data. Clients, Stakeholders, and Vendors are read-only: they view details, download documents, and open the Project Summary. When your roles are combined, the most permissive one wins, so a Vendor who is also a team member can edit. Project deletion requires both administrator status and edit access to the project.

02

Portfolio

The Projects page lists only projects visible to your account. It shows each project's name, project ID, overall completion percentage, and the first in-progress step by ascending step priority with its owners.

Search filters by project name, project ID, task name, or JIRA ticket ID. Filters narrow by task status, task owner, and due date. Clear filters to return to the full visible portfolio. Every member picker — task owners, meeting attendees, membership roles — lists only members who already hold a membership on a project you can see, so a user with access to one project cannot enumerate the member directory.

03

Project records

Create a project with a unique project ID and a name. The creator is added to the Project Team as its Project Manager, so they can staff it straight away. Record the description, scope, estimated completion date, actual start and completion dates, owner departments, development technologies, test and production servers, and any project documents.

Use Project roles to add a member, tick one or more roles, and record a responsibility. Several roles can be assigned in a single submission, which is how someone ends up as, say, both Developer and Delegated PM. Each role is a separate entry, shown as a tag on the project detail page and removable on its own — removing one role leaves the member's other roles intact. Adding a role they already hold is skipped rather than duplicated.

The activity history shows who created, changed, or deleted project data and when, with actor and project name snapshots preserved so the history stays understandable if an account or project is later removed.

04

Project Summary

The Project Summary page (/projects/<id>/summary) is the clean landing screen — the first thing you see after clicking a project from the portfolio or detail view. It is available to every project role, including Delegated PM and Delegated Backup. It is 404 for everyone else.

Always-visible pulse row

Four tiles answer the question "is this project OK?" without opening any section:

  • Completion — the step-weighted percentage, matching the figure on the project detail page and in the Project Manager status digest.
  • Next milestone — the name of the soonest upcoming milestone, or "None scheduled".
  • Needs attention — count of tasks that are blocked, overdue, or otherwise at risk.
  • Next meeting — the date and agenda of the next upcoming meeting, or how many meetings have been held.

Nine accordions

Every section is collapsed under a native <details> accordion by default. Click any heading to expand. No JavaScript is required.

  • Scope and timeline — project description, scope, estimated completion, actual start/completion dates, and overall completion percentage.
  • Milestones — achieved milestones with their achievement date, and upcoming milestones ordered by due date (undated milestones last). Each links to its owning task.
  • Key highlights — every key mark recorded on any task, grouped by label (Key Amendment, Key Finding, Key Decision, and any labels an administrator configured). Each shows the date it was recorded and links to the owning task. Marks survive the administrator removing a label from the picker.
  • Current tasks — active tasks showing status, completion percentage, the first in-progress step, the responsible member, milestone flag, and any highlight badges.
  • Blocked, overdue and at risk — tasks that are blocked, past their due date, or flagged as needing attention.
  • Meetings — every meeting with its agenda, date, attendee count, external guest count, location, and a Join in Teams button for future meetings that have a start time.
  • Documents — every uploaded file with its name and description.
  • Project team and responsibilities — every person on the project with their role, responsibility, team roles, and a mailto: link.

A Full project details link opens the full detail view where project-team members can create and edit tasks, steps, meetings, and memberships.

Breadcrumbs appear at the top of every hierarchical screen: Home > Projects > Project name > Summary, with the current page marked aria-current="page".

05

Tasks and progress

Tasks have a type (Development, Testing, UAT, Bug Fix, New Feature, Enhancement), a status (Not Started, In Progress, Blocked, Completed, Cancelled), a priority, a weight, an optional due date, an optional JIRA ticket ID, one or more owners, and ordered steps.

A task is a result of the Project Plan by default, or can reference a meeting on the same project. The source is shown on the task row so you always know where the task came from.

JIRA IDs become browse links using the JIRA browse URL setting, which an administrator can change at any time on the /settings screen without a restart.

Steps and completion

Project completion is the weighted average of every step: each step percentage is multiplied by its parent task's weight, and each step contributes that task weight to the denominator. A project with no steps reports 0%. Tasks without steps do not contribute to the calculation.

The current step is the first in-progress step by ascending priority. If no step is in progress, the task shows "No in-progress step".

Task ownership

Every task has one or more owners. The first owner is shown as the responsible member on the summary and detail pages. Task owners receive end-date reminders, stale-task nudges, and overdue alerts.

06

Key marks and milestones

Key marks

Every task carries an optional set of key marks — labels such as Key Amendment, Key Finding, and Key Decision. The list of allowed labels is maintained by an administrator on the /settings screen under task_highlight_types.

Applying a mark records it on the task with a date. Removing a label from the setting stops it appearing in the picker on new and edited tasks, but keeps it visible on any task that already has it and on the Project Summary — so no evidence is ever lost mid-project.

Marks appear as coloured badges on the task row and in the summary's Key highlights accordion.

Milestones

A task can also be flagged as a Milestone — a separate concept from a key mark. Milestones are scheduled checkpoints ordered by due date.

The first time a milestone task reaches Completed, its achievement date is stamped automatically. An explicit date always wins over the auto-stamp, and the auto-stamp is written only once — re-saving an unrelated field never rewrites it.

Milestones appear in the pulse row, the Milestones accordion (achieved first, then upcoming by due date), and the MCP summary and tools.

Who can use them

Project Team members can apply marks and set milestones when creating or editing a task. Clients, Stakeholders, and Vendors see them read-only on the summary and detail pages.

07

Meetings and Teams

Project Team members add a meeting date, optional local time, location, agenda, attendees, and notes. Attendees are a list of tick boxes: when you create a meeting every member on the project is pre-checked, so unticking is the only action needed to narrow the invitation. When you edit a meeting only the current attendees are pre-checked, so saving an unrelated change never adds people the meeting did not originally include.

Ad-hoc attendees — comma-separated email addresses for one-time guests who have no member account (such as an external consultant). Addresses are validated, lowercased, and de-duplicated. They receive Teams compose links and reminder emails but gain no project access and are not added to the member directory.

Teams compose links

When a meeting has a future date and a start time, saving it opens a prefilled Teams meeting/new compose link. The link carries the project meeting subject, agenda, all member attendee and ad-hoc guest email addresses, and a 30-minute time range, in the creator's browser timezone.

The link is a compose link, not Microsoft Graph integration — the organizer reviews and sends the invitation from Teams.

On the Project Summary — every future meeting with a start time shows a Join in Teams button in the Meetings accordion and on the pulse tile. This lets any project member (including Stakeholders and Clients who were not invited) open Teams and join.

Past meetings and meetings without a time do not open Teams.

Action tasks

Create action tasks directly from a meeting record. The task retains the meeting as its source, so you can always trace a task back to the meeting where it was decided.

08

Members and servers

Administrators manage member profiles and server records from their separate screens. New member passwords must be at least 12 characters. Server records include IP address, operating system, and technology/packages.

The Members screen lists every member account with name, email, designation, organization, and an Admin tag for administrators. Each row has an Edit and Delete button. You cannot delete your own administrator account, and a member with project roles or task ownership must be removed from those first.

The Servers screen lists every server with its name, IP, operating system, and packages. Servers are assigned to projects from the project detail page.

Only members created with flask --app mizalla create-admin or the Members screen by an existing administrator have administrator access.

09

Services

Five services sit outside the project records: Bulk Emailer, Bulk Messenger, Vision, Speech, and Chat. There is no separate services landing page — each one is a link in the header beside Bulk Emailer and Bulk Messenger, alongside the other apps. Every one of them is granted per member by an administrator, and every one of them enforces that grant on the server — a bookmarked or typed URL for a service you were not given returns 403 rather than the form.

Granting access

Open Members and edit the member. The Service Access fieldset lists every service as a checkbox; untick to revoke. Granted services appear as tags next to the member's name on the Members list. Administrators always have access to every service, so they can verify one before rolling it out. The older single "Has access to Bulk Emailer" checkbox is gone: every service is now granted the same way, and existing Bulk Emailer members were migrated automatically on first start.

When a service has no credentials

Two things decide what the header shows, and they are independent.

  • Access — a service you were not granted is left out of the header entirely, so it does not advertise itself. Typing its URL still returns 403.
  • Credentials — a service you were granted but that has no keys is still listed, greyed out and not clickable. Hovering it names the exact .env variable an administrator has to fill in. Being granted a service does not conjure its credentials.

Opening a service page without credentials returns "not available" and the same list of missing variables, rather than a form that could only fail. The Settings screen carries an Azure service credentials panel showing a tick or a cross per service and, for anything missing, the .env variable names in red.

Bulk Emailer and Bulk Messenger

Bulk Emailer sends a templated message to a recipient list from a CSV file, with {{placeholder}} substitution in subject, body, and attachments. Bulk Messenger sends the same kind of templated message through a registered WhatsApp device. Both require a device or service grant, and the WhatsApp screen first checks that the GOWA server is reachable — if it is not, sending is disabled with the reason shown rather than a form that would time out.

Vision Test Service

Upload an image with Browse or by dropping it on the target. One Azure Vision call returns the text it reads from the image on the same page:

  • Recognised text — every line Vision read, which is what the mapping below is resolved against.
  • Mapped fields — named values pulled out of the response by the administrator's mapping, each labelled with how it was resolved.
  • Service JSON — the entire response, collapsible, exactly as Azure returned it.

The mapping is JSON entered by an administrator in Settings. Each value is tried as a path into the Vision response first, then as a label to look for in the recognised text, then falls back to the whole recognised text. The default {"ID": ""} means "give me the ID", resolved to whatever text Vision read off the image. Because the fallback is the whole text, a field that resolves wrongly is visible rather than silently blank, and the "Resolved by" column tells you which of the three rules fired.

Speech Test Service

Type text (up to 5,000 characters) and it comes back as an audio clip with a player on the page. The Voice list is grouped by accent: four English accents — US, UK, Australia, India — with two male and two female voices each, then four Arabic accents — Egypt, Saudi Arabia, Morocco, Qatar. Clips are kept briefly and only you can play your own; older ones for your account are cleaned up automatically.

Each Arabic accent offers one male and one female voice rather than two of each. Azure publishes only that pair per Arabic locale, so there is no fourth voice to select; the list shows every voice that exists rather than padding itself with names Azure would reject.

The list is a fixed catalogue of real Azure voices rather than a free-text box, so a mistyped name cannot turn into an opaque "voice not found" from Azure — an unrecognised choice is refused with a message pointing back at the list.

Chat Service

Add documents with Browse or by dropping them on the target — PDF, DOCX, DOC, XLS, XLSX, PPT, PPTX, TXT, MD, CSV, and RTF. The text is extracted, split into searchable sections, and indexed. Then ask a question in plain language.

Answers are built only from the sections that match your question, and every claim is cited by number so you can check it. Each answer lists its source extracts with the document name, the section heading, and how much of your question's wording it covered — so you can see why it answered what it did. If nothing in the documents matches, the service says so rather than answering from general knowledge. Follow-up questions carry the previous exchange forward.

Two caveats worth knowing: retrieval is keyword-based, so a question phrased very differently from the document may match nothing even when the document covers the topic; and the library is shared by everyone with Chat access, so one member's upload can answer another's question. Legacy .doc and .xls files are read by scraping printable text, which is approximate — PDF and DOCX extract far more reliably, and the app says so when it has used a fallback.

Upload File

Stores a file in a folder on the server and lists everything already there. Accepted types are PDF, TXT, DOCX, XLSX, PPTX, PPT, DOC, HTML, HTM; anything else is refused with a message naming the accepted list. No credentials are needed, so this service is never shown greyed out.

The folder is shared, so every member with access sees the same files, and the list shows who uploaded each one. Each file keeps the name it arrived with while being stored on disk under a generated name — two members can each have a report.docx without one overwriting the other. You can delete a file you uploaded; an administrator can delete anyone's.

Every download is saved rather than opened in place, including HTML. That is deliberate: an uploaded page could otherwise contain script that runs in this app's own address when another member clicks it. Your browser saves the file and you open it yourself, where it is just a document.

Where the Azure credentials live

Every Azure Vision, Speech, and OpenAI credential is read from the application's .env file and nowhere else. They are not settings, are not editable on the Settings screen, and are never written to the database — which also means they do not appear in a database backup or in a screenshot of the settings page. Adding one is a deployment change: put it in .env and restart the application.

The variables are MS_VISION_ENDPOINT and MS_VISION_KEY for Vision; MS_SPEECH_KEY with MS_REGION (or a full MS_SPEECH_ENDPOINT, from which the region is read) for Speech; and AZURE_OPENAI_ENDPOINT, AZURE_OPENAI_KEY, and AZURE_OPENAI_DEPLOYMENT_NAME for Chat. The Settings screen shows only whether each one is present, so an administrator can confirm the state without the value ever being displayed, entered, or stored.

10

Settings

The /settings screen is restricted to administrators and manages hot settings that take effect immediately across the web UI, API handlers, MCP tools, and email jobs — no restart required.

Setting types

Each setting shows its key, current value, a badge indicating whether it is at its Default value or has been Modified, and an optional hint explaining the setting. Settings whose effective value differs from the stored value show an "In effect now" notice revealing which source wins.

  • JIRA browse URL — the base URL for rendering JIRA ticket IDs as browse links.
  • Project team roles — the comma-separated list of allowed team roles. Used for the project team role pickers and the project_team_roles setting.
  • Task highlight types — the comma-separated list of allowed key mark labels (e.g. Key Amendment, Key Finding, Key Decision).
  • App base URL — the base URL used in generated links and email content.
  • Email thresholds — days between status reports, task reminders, stale nudges, overdue digests, and meeting reminders.
  • Azure Vision — the vision_id_mapping JSON that decides which fields are extracted from the response and how. A mapping that is not valid JSON is reported on the Vision page and falls back to the default rather than breaking the service.
  • Azure OpenAI — how large a document section may be (chat_chunk_chars) and how many sections a single answer may draw on (chat_max_chunks).

Managing settings

Each setting row has a Reset to default button that restores the built-in default value. The Save Settings button validates label lists before writing — if a label list contains invalid entries, the error is displayed and nothing is written. A label list that passes validation is saved immediately and takes effect everywhere.

Resolution order is database → boot configuration (process environment / .env) → built-in default. A database value is an administrator override and always wins. The environment value seeds a fresh database and is used when no override exists. Only SECRET_KEY, SENDGRID_API_KEY, and the Azure Vision, Speech, and OpenAI credentials are env-only and never hot settings.

11

Security and stored data

State-changing forms use CSRF protection. Uploaded documents are stored with generated names under the configured instance upload directory and are available only to project members. Every document download goes through a membership check and, optionally, a cryptographically signed time-limited token.

Service grants are enforced on the server, not by hiding links, and they are separate per service — holding Chat does not imply Vision, and neither implies Bulk Emailer. Uploads to the services are checked by extension and by file signature, so a renamed executable is refused. Synthesised audio is stored under the instance folder and served only back to the member who created it, under a filename that must match that member's ID. Azure keys are stored in the settings table and are never shown in a service page.

Local development generates a signing key at instance/.secret_key (git-ignored). Production should provide a persistent SECRET_KEY environment value and serve Flask behind a production WSGI server with HTTPS and SESSION_COOKIE_SECURE=true.

Error handling — styled error.html pages handle 403, 404, 500, and 413 errors with a link back to the portfolio. The 404 page deliberately names no project, so a hidden record does not leak its existence.

SQLite schema changes are additive. Back up the database and uploads together. The built-in Flask server is intended for local development only.
